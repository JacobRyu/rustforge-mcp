# 設計意図と設計上の考慮（Design Intent & Rationale）

このドキュメントでは、rustforge-mcp の**設計の意図**と、**なぜこの設計を選んだのか**という考慮ポイントを説明します。
完成図は [ROADMAP.md](./ROADMAP.md)、現状実装は [IMPLEMENTATION.md](./IMPLEMENTATION.md) を参照してください。

---

## 1. 全体設計の意図

### 1.1 問題意識（なぜこのプロジェクトが必要か）
AI エージェント（Claude / Gemini など）が Rust 開発を支援する際、以下の課題がある:

- **実行環境との疎通**: エージェントがファイルを読み書きし、`cargo` を実行するための安全・標準化されたインターフェースが無い。
- **バックエンドの多様化**: 利用可能な MCP / LLM プロバイダが複数あり、エンドポイントごとの稼働状況・性能・重みが異なる。単一固定の接続では可用性・性能・コストを最適化できない。

この 2 つの課題を 1 つの Rust プログラムで解決することを意図しています:
1. **直接操作ツール層** = Rust 開発を強力に支援する MCP tool set
2. **ルーティング基盤** = 複数プロバイダをスコアリングして最適なものを選ぶ「ゲートウェイ」

### 1.2 MCP の採用理由
- Model Context Protocol（MCP）は、モデルとツールの接続を標準化する業界標準。
- `rmcp` クレートでサーバ実装が簡潔になり、Claude Desktop / Gemini CLI などの既存クライアントがそのまま接続できる。
- `#[tool]` + `schemars` による自動スキーマ生成で、ツール定義を宣言的かつ型安全に記述できる。

## 2. 主要な設計判断とその理由

### 2.1 Storage をトレイト（`Arc<dyn Storage>`）で抽象化した理由
```rust
pub trait Storage: Send + Sync { ... }
```
- **目的**: 永続化実装を実行環境に応じて切り替える（本番=PostgreSQL、開発/テスト=InMemory）。
- **考慮点**
  - `Arc<dyn Storage>` で複数タスク（API / ヘルスチェック / ルーティング）が同一 storage を共有できる。
  - `Send + Sync` + `async_trait` で、`tokio` タスク間を跨いで安全に使用可能。
  - トレイト抽象により、将来の実装（他の DB、キャッシュ層）を追加する際に呼び出し側を変更しない。

### 2.2 ルーティングを「スコアリング関数」で実装した理由
```rust
score = weight - (latency_ms / 20) - (error_rate * 100) - health_penalty
```
- **目的**: 単なるラウンドロビンやランダムではなく、複数要素を合成した「適応的な選択」を行う。
- **各項の意図**
  - `weight`: 管理者が指定する明示的な優先度（既定 100）。
  - `latency_ms / 20`: レイテンシが 20ms 増えるごとに 1 点減点。応答速度を反映。
  - `error_rate * 100`: エラー率 1% ごとに 1 点減点。安定性を反映。
  - `health_penalty`: ヘルス状態による明示的ペナルティ（Degraded=40 など）。切替ハステリシスを生む。
- **考慮点**: `metadata`（JSONB）に `last_latency_ms` / `error_rate` を動的に格納する設計は、**スキーマ変更なしで採点材料を追加**できる柔軟性を狙っている。

### 2.3 Health Check Worker を独立タスクで動かす理由
- ルーティングの品質は「選ぶ前にエンドポイントが healthy かどうか」に依存する。
- 独立した 60 秒周期 Worker が事前に health / latency を更新し、`route()` はその情報を読むだけにすることで、**リクエスト毎にヘルスチェックをする必要をなくす**（分離関心・低レイテンシ）。
- 応答に応じて `Healthy` / `Degraded` / `Unhealthy` を区別し、`metadata.last_latency_ms` を採点に活かす。

### 2.4 認証をミドルウェアで一括適用する理由
- 管理 API は機微情報（API キーを含む `ServerEndpoint`）とルーティング操作を担うため、外部から保護が必要。
- `middleware::from_fn_with_state` で全ルートに一括適用し、個々のハンドラに認証ロジックを散在させない。最小限の設計ながら「HTTP API は認証必須」という境界を明確化。

### 2.5 `ServerView`（api_key 除外）でレスポンスを分けた理由
- `ServerEndpoint` は `api_key` を保持するが、これをそのままクライアントへ返すのは不適切。
- `ServerView` を `From<&ServerEndpoint>` で導出し、**公開レスポンスから秘密情報を剥がす**構造にした（情報漏えい防止の設計原則）。

### 2.6 ルーティング履歴 / 監査ログのテーブル設計
- `routing_history` は「どのサーバが、なぜ選ばれたか」を理由付きで保存し、意思決定のトレーサビリティを確保。
- `audit_logs` は操作監査（誰が何をしたか）の土台。実装後は `POST /servers` / `DELETE /servers/{id}` / `POST /route` で自動記録し、`GET /audit-logs` で閲覧可能。

### 2.7 ルーティング戦略を複数持たせた理由
- 単一のスコアリングだけでは、用途によって望ましい選択が異なる（例: 可用性→Score、負荷分散→RoundRobin、コスト分散→WeightedRandom）。
- `RoutingStrategy` enum + serde で env 既定戦略とリクエスト単位の上書きを両立。
- 実装は `select_*` メソッドに分離し、戦略追加を局所化。

### 2.8 サーキットブレーカーを導入した理由
- ヘルスチェックの失敗が連続するサーバへトラフィックを送り続けると、利用者は不必要にエラーを体験する。
- `consecutive_failures` を `metadata`(JSONB) に保持し、閾値（3）超で選択対象から除外。回復（Healthy）で自動リセット。
- スコアリングの減点要素（`failures * 15`）も組み合わせ、即時遮断と段階的減点の両方を提供。

### 2.9 API キーを保存時暗号化した理由
- `api_key` が DB に平文で残ると、DB 漏えい時に外部プロバイダの資格情報が全て露出する。
- `ENCRYPTION_KEY`（AES-256-GCM）で保存時に暗号化し、読み出し時にのみ復号（`PostgresStorage` が透過的に処理）。
- 開発用途（インメモリ・暗号キー未設定）では平文のまま明示的な警告を出す。暗号化の設定差異を `Crypt` で抽象化。

### 2.10 コマンド実行を安全化した理由
- MCP ツールが `cargo` を任意引数で実行できるのは強力だが、`publish`・`clean` やインジェクションに悪用されると危険。
- **許可リスト**（`CARGO_ALLOWED_COMMANDS`）で実行できるサブコマンドを制限。
- **シェルメタ文字検証**で `; | & $ ( ) < >` 等のインジェクションを拒否。
- **タイムアウト**で暴走コマンドを防ぐ。
- **パス制限**（`WORKSPACE_ROOT`）でファイル操作をワークスペース内に閉じ込め。

### 2.11 RBAC（Admin / Viewer）を導入した理由
- 読み取り専用の運用監視クライアント（ダッシュボード等）に書き込み権限まで与えるのは過剰。
- `VIEWER_API_TOKEN` を付与されたクライアントは GET（一覧・監査・metrics）のみ可能にし、書き込み系は Admin に限定。
- 認証ミドルウェアが `Role` をリクエスト拡張に注入し、`require_write` ミドルウェアで書き込みルートを保護。

## 3. 設計上の明確なトレードオフ・残課題（技術負債）

- **MCP プロバイダは streamable HTTP のみ**: MCP の stdio / SSE トランスポートには未対応。SSE はトランスポート切替で対応可能だが、現状は streamable HTTP に統一。
- **同期実行前提の MCP**: `main.rs` のコメントにある通り、stdio はターミナルを占有する。完成形ではコントロールプレーンと MCP サーバを分離する想定（[ROADMAP.md](./ROADMAP.md) §4）。
- **暗号化キーのローテーション未対応**: キー変更時の既存データ再暗号化運用は今後の課題。
- **API キーはレスポンスで常に秘匿**: `ServerView` で除外する設計は安全だが、監査やデバッグ時に利用不可となる点は運用上のトレードオフ。
- **InMemory の非永続**: 開発用途を明確に想定し、再起動でデータが消える旨を warn ログで明示。

## 4. 設計原則のまとめ

- **関心の分離**: ツール層 / API / ストレージ / ルーティング / 可観測性 / セキュリティ をモジュール単位で分離。
- **インターフェースによる抽象化**: `Storage` トレイトで永続化を差し替え可能に。
- **宣言的・型安全**: MCP ツールを `#[tool]` + JsonSchema、モデルを強く型付け。
- **スキーマの柔軟性**: `metadata`（JSONB）で採点材料・回路状態を動的に拡張し、スキーマ変更不要を実現。
- **情報最小公開**: `ServerView` で秘密情報をレスポンスから除外。
- **設定可能な安全性**: コマンド許可リスト・パス制限・タイムアウトを環境変数で運用調整可能に。
- **デフォルト安全・明示的警告**: 暗号キー未設定時は暗号化を諦める代わりに明確な警告を出す。
- **段階的構築**: 基盤を先に作り、接続層・安全化・運用拡充を段階的に追加する設計方針を維持。
